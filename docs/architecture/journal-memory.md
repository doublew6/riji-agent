# 日记长期记忆：实施设计

状态：来源生命周期、权限控制与可选 Codex 模型的实施设计。对应 [Issue #40](https://github.com/doublew6/riji-agent/issues/40)，依赖 #39 的 Mem0、捕获队列及 Review 接口。部署方法见 [验收说明](../codex-provider-air-2026-09-09.md)；真实覆盖及私人运行记录不随仓库发布，代码通过不等于质量验收完成。

## 组件与处理顺序

本地来源发现与段落解析 → 持久任务 → 模型提取结构化候选 → 同范围相关记忆检索 → 关系判断 → 本地校验及显式写入 → 证据与状态更新 → 召回及 Review。

日记扫描与原有检索索引分开维护水位，因此索引成功不代表记忆已形成。原生聊天捕获继续使用原入口。Mem0 保存权威记忆内容；新的本地 SQLite 保存来源、段落指纹、任务、证据关联、阶段关系、处理预算与遗忘抑制。向量化继续由 Mem0 的本地 FastEmbed 处理。

## 授权和默认值

- 新日记捕获默认关闭；启用必须指定一个白名单用户及允许出云的日记区块。根目录沿用 `RIJI_JOURNAL_ROOT`，不扫描整个 Obsidian 库。
- `daily`、`weekly`、`monthly` 下递归发现 Markdown；排除隐藏目录、模板、附件及符号链接。未知日期保留未知；不可读文件显示失败。
- 区块由显式标题清单选择；默认建议 `🧠 Notes`，不是整个文件出云。扫描状态区分范围排除与处理失败。
- 单片段 900 字符、同一文件版本累计 4000 字符；日常日记处理每 UTC 日 100000 字符，模型提示词、证据和旧记忆都计入。用户授权的本次固定历史批次独立计量，不设每日总量上限；单次和来源上限仍适用。旧 40000 字符策略仅保留为历史验收记录。
- 初始化期间和之后定期扫描；文件日期不充当增量水位。正文和日期参与段落指纹；重复通知与重启复用任务和已提取结果。

具体参数、稳定保存、目录分母与恢复语义见 [操作说明](../journal-memory.md)。每日请求预算与同一来源原文预算分开累计，不等价于模型 token 计费。

## 历史批次与日常预算

`RIJI_JOURNAL_MEMORY_DAILY_CHARS` 默认 100000；`RIJI_JOURNAL_MEMORY_INITIALIZATION_UNLIMITED` 默认 `false`。后者显式启用后，按 scan → grant → resume 顺序冻结一次批次：SQLite `initialization_evidence` 只包含已授权 `privacy_history(id,version)` 与当前有效日记证据版本的交集。未扫描或授权清单为空时保持 `awaiting_scan`；空授权后新出现的文件不能自动成为历史。后续 grant、scan、retry 均不扩充已冻结清单；不能仅凭“文件日期较早”或开关仍为 `true` 判定豁免。批次启用后新增的文件、补入的旧日期日记及被修改后的新版本，均继续走日常增量预算。

批次内提取、关系判断及以本批产出记忆为种子的必要有界整理，使用 `initialization:UTC-day` 账本独立记录字符量，并保留来源版本及阶段审计，不挤占普通日预算。旧 `day:` 账本不清零、不追溯转移。普通种子整理、后续增量及常规日记整理使用每日 100000 字符额度。初始化运行不能变成豁免全用户后台任务的条件；已确认的原生聊天预算和受限问答边界仍独立。

预算策略生效时，当前批次中仅因旧每日额度而等待的任务应立即重新具备领取资格，不等待旧的次日时间戳。保留提取缓存、操作 ID、来源累计量与审计，不能通过清空账本或重建作业恢复。权限、源版本、模型额度、登录及其他失败原因仍需各自检查。

批次提取达到终态且必要整理完成后持久关闭豁免，后续处理恢复日常预算；开关继续为 `true` 也不能重新开启。失败或预算等待不能伪装成成功；暂停、撤权和失效状态仍阻止相应调用。重启加载原批次进度，不自动创建新无限批次。

`engine.initialization_status()` 与 `privacy.status()['initialization']` 提供 `enabled/state/active/total/pending/completed/excluded/failed/organization/request_chars`，以及 `recovery_pending/recovery_spent/recovery_active/exemption_active`。`organization` 单列整理状态；`request_chars` 汇总本批各 UTC 日账本，是跨日累计量。提取与必要整理均达到终态后，无失败时持久状态为 `completed`，有失败时为 `blocked`，两者均停止原批次初始处理豁免，后者不得显示为全部成功。`active` 只表示原批次仍在初始处理，不因有限恢复而重开。

用户于 2026-09-10 确认本固定批次的一次整理恢复也归入初始化预算。`initialization_recovery(id,version)` 的显式登记、原种子的首次发送记录、尚未发送的恢复记录及当前 / 冻结 / 策略范围一致，共同限定有效恢复；配置关闭或批次 `cancelled` 时不适用。领取时原子检查并消费一次恢复，按 `initialization:UTC-day` 计量；此前已计入 `day:` 的请求不追溯转移。已发送的恢复不能再次领取，失败或成功后保持终态。该路径可以在原批次 `blocked` 或 `completed` 时处理已登记的恢复，不改变原批次为 `active`，不纳入新文件、新版本或普通种子。

`recovery_pending` 仅计当前适用初始化账本的未发送恢复；`recovery_spent` 计同范围已发送待结果的恢复，避免最后一次请求执行时误报关闭。`recovery_active` 为上述两项合计大于零，`exemption_active` 为原批次或有限恢复尚适用的预算状态；它们不是跳过暂停、授权或发送前校验的条件。Review 显著区分总恢复队列与适用初始化账本的恢复数量，同时展示日常已用 / 上限、初始化累计、原批次状态和实际覆盖。无每日总量上限不代表不计量、整库上传或 Codex 套餐无限。

## 记忆与证据

候选包含内容、类型、明确自述 / 推断、有效日期及原文证据。来源 ID、归属与段落位置由程序分配。模型只提出新增、重复、补充、状态变化、冲突或相关关系；程序检查目标 ID、用户、导师、来源和目标版本，以及人工修订和遗忘状态。

同一事实的重复表达可增加证据；补充和状态变化保留可回顾的版本与关系。当前状态按事实时间判断，不按入库顺序判断；未知时间或未解冲突不静默覆盖。读路径在返回日记派生记忆前验证有效依据；源变化、删除或撤权即停止使用旧依据，随后后台重算。

## 恢复与验收

SQLite 任务持久化、租约领取、已提取输出缓存与操作标识支持重试。写入前再次检查来源与目标版本；调用结果不确定时先按操作标识查验后端。删除保留最小指纹抑制，清理活动派生材料；备份恢复先重放本地遗忘记录，再开放召回。

实现使用合成目录和受控模型 / 后端验证确定性边界。真实模型准确性、时序判断和 Air 端到端验证单独报告，不能用测试替身代替。既有日记写入、模板、身份隔离和原生聊天均须回归。

## 一致性与组件契约

- `journal_store.py` 持久保存源清单、证据指纹、作业租约、缓存、操作状态、关系、时间阶段和抑制；目录扫描使用进程锁。权限变化作废正在执行的旧租约。
- `journal_extract.py` 中的 Schema、抽取提示词和关系提示词随代码管理；本次开发试验版本标识及样本见 `evals/journal-memory/README.md`。模型只有结构化输出权限，没有工具、文件写入或删除权限。
- `journal_engine.py` 先记录操作，再通过 Mem0 管理扩展显式写入；两边不假设分布式事务。源或目标版本变化时保持未登记结果不可召回，重试按操作 ID 查找，最后登记有效证据关系。
- `journal_backend.py` 是检索、Review 和快照共同的有效性入口；逐条验证当前源片段。删除先抑制，再重试后端清理；相关解释不能保留已遗忘目标的正文。
- `journal_organization.py` 保存跨批次覆盖进度，查询有界相关事实并检验独立经历；观察在召回时再次验证报告版本、来源、用户和导师。
- `journal_transfer.py` 导出结构化本地数据；恢复先暂停并合并抑制，再建立新的 ID 映射，重新扫描本机来源，成功后仍保持暂停。
- 旧 SQLite provider 继续支持既有能力；新关系和证据元数据不宣称能通过切换 provider 无损回退。保留 Mem0 与运行库备份，按恢复流程回退数据。

原生聊天能力沿用 #39，日记模型提取独立于检索索引。新增段落引用原文件行号与版本；未知日期不以导入时间替代。阶段按明确生效时间判断；人工纠正及独立原生聊天可以成为日记源之外的依据。

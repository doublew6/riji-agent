# 导师私聊与群聊体验提升讨论稿

让用户先自然地聊天，需要时再整理内容。保留首页的北极星与人物空间，聊天页把注意力交还给消息、说话的人和输入框。

先看[可交互方案图](../../output/mentor-ux-review-2026-10-16/experience-plan.html)或[方案总览图](../../output/mentor-ux-review-2026-10-16/proposal-board.png)。图中是建议效果，不是已实现界面，也不代表真实服务已经可用。

## 1. 本稿的确认状态与范围

用户先要求“整体检查一下，给出一个提升体验的方案”，随后于 2026-10-16 明确“开始修改”。本轮按已说明的第一批执行 UX-01/03/04/05/06/09：消息按需操作、单份最终保存预览、状态与连接说明、连续输入、群名保存。实施与验证见[开发规格](../../_bmad-output/implementation-artifacts/spec-56-mentor-chat-usability.md)。第二批和文中明确标注的产品选择继续待讨论，不因本轮实施扩大确认范围；首页 F 视觉、消息左右布局和四个主导航保持。

第一批代码已落地；185 个相关 Core/State 用例和 8 条不同原生交互流程已通过。2026-10-17 解锁后补完群聊保存精确追加与冷启动回归；[实际界面与最新验证记录](../testing/ios-mentor-usability-2026-10-17.md)同时记录保存后日记露出内部来源信息的待改问题，不把数据完整性通过等同于全部体验验收。

| 继续保留的已确认内容 | 本稿如何沿用 |
| --- | --- |
| F · 北极星指引：沉静、暖光、空灵宇宙感 | 首页保持既有人物、深绿空间、克制的北极星；不重做品牌和人物 |
| 每位导师唯一私聊 | 仍从首页上方人物进入，不在下方重复列私聊 |
| 首页下方每群一行，点入就是消息 | 不恢复“记录总入口”或另一层人物首页 |
| 群可讨论固定话题，也可长期使用 | 不新增话题类型、会议模式或必填背景 |
| 聊天保留与日记写入不同 | 消息正常保留；写入日记须主动选择、预览、确认 |
| 群成员就是实际信息接收范围 | @ 仅选择回应者；私聊、其他群、北极星材料不会自动分享 |

范围是“导师首页 → 私聊/建群 → 群聊 → 找回记录 → 保存到日记”，并检查北极星、AI 服务连接与这些流程的交接。没有评审整个 App 的日记编辑器、记忆系统或设置架构。

依据为[导师私聊与群聊 PRD v0.3.2](../../_bmad-output/planning-artifacts/prds/prd-riji-agent-2026-10-14/prd.md)、[F 视觉基线](../design/mentor-dialogue.md)、[全局设计规范](../DESIGN.md)和当前源代码。

## 3. 建议用户感受到的使用方式

```text
导师首页
  ├─ 点一位人物 → 这个导师的原私聊 → 直接说话
  ├─ 点一个群   → 这个群的原消息   → 直接说话 / @ 某位回应
  └─ 点＋建群   → 选导师 → 创建    → 直接说话

任意一条消息
  └─ 长按 → 复制 / 保存到日记 / 多选
                  └─ 一份最终预览 → 明确确认 → 保存成功，可查看
```

建议的聊天样式：导师消息在左侧，用户消息在右侧；小头像和姓名帮助分辨导师；时间在必要位置出现。AI 身份保持清楚，聊天页可显示“AI 导师”，消息详情与日记来源继续明确标注 AI 建议，不暗示真人在线。无需在每条普通消息前重复大标题、卡片框与操作控件。

群聊天顶部保留简洁群名、成员信息与北极星入口。建议优先比较进入聊天后隐藏底部主导航的方案，以增加阅读空间；这仍属于待讨论布局选择，不能仅为多出空间而破坏返回、无障碍或切换草稿的路径。

## 4. 十二项提升建议

优先级表达实施顺序：P0 是影响“能否理解并安心完成核心动作”的优先修正，P1 是高频聊天与找回记录，P2 是次级管理便利性。它们不是已证明的数据损坏或安全漏洞等级。

### UX-01 · P0 · 常驻勾选改为按需出现的消息操作

**场景：** 用户阅读导师建议，看到右上角的圆圈或勾，不知道是否代表已读、完成、采纳或保存。

**实现事实：** 每条可用的群 AI 消息常驻选择按钮；有选中时，输入区出现“每次保存同一轮的最多五段回复”“保存选定结果”。见 `ios/Riji/MobileRoundtableViews.swift:120`、`:191`。这是本轮截图与用户提问直接证实的理解问题。

**之前：** 看消息 → 猜测圆圈用途 → 勾选 → 才发现保存按钮。

**建议：** 长按消息 → 明确的“复制 / 保存到日记 / 多选”。只有主动进入多选模式才显示勾选、数量与取消；普通聊天不出现选择状态。保存选择跨轮次的限制由系统判断并就地解释，不默默清掉用户原选择。

**确认状态：** 用户已认同长按保存方向；菜单细节、多选上限与跨轮次处理仍需细化。

### UX-02 · P1 · 用消息左右关系替代整页同向大卡片

**场景：** 几位导师连续回应后，用户想快速分辨自己问了什么、谁回复了什么。

**实现事实：** 用户与导师共用全宽、左对齐的 `MentorSpeakerCard`；每张卡显示姓名、内容性质、边框，普通导师头像为 48 × 56。见 `ios/Riji/MentorDialogueStyle.swift:165`、`:182`、`:190`；群与私聊调用分别见 `ios/Riji/MobileRoundtableViews.swift:116`、`ios/Riji/MobileViews.swift:318`。

**体验判断：** 连续全宽卡片缺少熟悉的左右区分，标题与承托挤占阅读空间。这是源代码与已有截图支持的布局判断，尚未进行本轮对比可用性测试。

**之前：** 多张相似卡片 → 逐张读“我 / AI 建议”才能分清角色。

**建议：** 用户右侧、导师左侧；导师小头像与姓名保留，正文是主体。连续同一发言者可减轻重复姓名，但不能合并掉真实消息边界。长段内容保持可选择、可滚动；时间按相邻消息间隔或日期分组出现。AI 身份在页面、消息详情和保存来源中始终可辨识。

**待讨论：** 左右消息布局及具体密度，属于本轮新建议，不追认为已批准视觉。

### UX-03 · P0 · 保存到日记只呈现一份可确认的最终预览

**场景：** 用户想把一条有价值的建议保存到今天日记，不想理解“选定结果、独立 AI 区域、本地版本核对”的内部流程。

**实现事实：** 当前先编辑日期/文本，再点“核对本地日记版本并预览”，出现渲染预览后另点“确认保存到本机日记”；修改时须取消预览。见 `ios/Riji/MobileRoundtableViews.swift:638`、`:653`、`:661`。确认与未知结果核对见 `ios/Riji/DiaryViewModel.swift:1857`。补充模拟器走查已观察到编辑与核验后预览的切换、同一短建议重复显示；最终确认与写入没有执行。

**之前：** 选消息 → 编辑页 → 手动发起核验 → 第二份预览 → 确认；要改字则取消后重来。

**建议：** 长按保存 → 同一页选择日期和编辑文字 → 自动完成来源及目标版本核验 → 在同一页展示本次**最终确切追加 patch** → 用户明确确认。核验等待不是另一项任务，界面显示“正在准备保存预览”；未完成时不能确认。修改文本、日期、来源或目标文件后，旧预览与确认资格立即失效，须重新核验并展示更新 patch。不能通过“单一页面”把未经预览的写入藏在按钮后面。

**必须保留：** 日记既有内容不重写；追加位置与确切文字清楚；幂等、原子写入、来源与 AI 性质完整；失败保留现场；结果未知先只读核对，不能重复追加。成功后显示“已保存到 10 月 16 日日记 · 查看”。日记文件版本变化时先处理冲突，再生成新的确切预览。

**待讨论：** 同一页预览与编辑的版式。技术核验与明确确认要求保持现行规则。

### UX-04 · P0 · 把运行回执变为用户能判断的消息状态

**场景：** 消息发送后网络断开，用户不知道是否应该再发一遍，或面对“核对后继续 / 结束本轮 / 原操作回执”不知如何选。

**实现事实：** 群页同时挂载发送、保存、停止、结束等 `MobileOperationView`；中断时有“核对后继续”和“结束本轮”；完成操作仍显示“服务已确认接收”。见 `ios/Riji/MobileRoundtableViews.swift:143`、`:201`、`:213`，`ios/Riji/MobileViews.swift:45`，`ios/RijiCore/MobilePersistence.swift:55`。

**之前：** 读取系统说明 → 分辨多个操作状态 → 自行核对原操作 → 再选继续或结束。

**建议：** 正常态只显示对应消息的发送状态，以及“直率教练正在回复 / 停止回复”。已成功的普通回执收起。未知送达时就地显示“正在确认是否送达，文字已保留”，自动只读核对原操作；需要用户决策时只提供当前合理主动作。详细回执、原请求编号和失败文字导出放“查看详情”。

**边界：** “暂时不知道是否送达”与“确认没有发送”必须区分；未知送达不可自动重发、另建群或结束后假称原请求不存在。停止请求未确认时不假称“已停止”；部分回复保留，可能迟到的回执仍回到原会话。

### UX-05 · P0 · 连接状态说清楚，并与真实服务能力一致

**场景：** 用户看到“连接未完成”，或看见群聊界面却在设置中读到“圆桌不在此连接中提供”。

**实现事实：** `connected` 只表示已有设备凭据，并非当前服务在线；transport 错误统一写“连接未完成…核对原操作”。设置中的两项恢复入口调用同一重试方法，能力说明仍固定排除圆桌。见 `ios/Riji/MobileClientModel.swift:60`、`:258`，`ios/RijiCore/MobileModels.swift:10`，`ios/Riji/MobileSettingsViews.swift:12`、`:28`。新群能力实际由 `group_chat` 决定，见 `ios/Riji/MobileRoundtableState.swift:5`。

**之前：** 模糊连接提示 → 重试连接 / 重新读取凭据两个入口 → 用户仍不能确认是离线还是尚未提供群聊。

**建议：** 区分“尚未连接 / 正在连接 / 已连接 / 暂时离线”，授权失效另明确“需要重新连接”。临时故障只有一个“重试连接”主动作；凭据恢复细节收进详情。按能力真实显示私聊、群聊和记忆：旧服务未提供新群时明确“此服务版本暂未支持建群，已有记录仍可查看”。

**边界：** 不把存在凭据等同服务在线；不把未部署等同网络故障；演示模式只在实际 fixture 启用时显示“演示环境 · 合成回复”，不能包装成真实模型接通。

### UX-06 · P0 · 输入不断、阅读位置不跳

**场景：** 用户发完一句马上补充另一句，或回看旧消息时正好收到导师回复。

**实现事实：** 群与私聊发送点击均先把 `composerFocused` 设为 false；使用顶部锚点、定时刷新和 `onChange` 恢复已保存阅读位置。见 `ios/Riji/MobileRoundtableViews.swift:148`、`:174`、`:231`，`ios/Riji/MobileViews.swift:337`、`:349`、`:377`。当前代码也已有“查看新回复”入口，不是完全没有阅读恢复。

**实测与风险：** 私聊在硬件键盘下输入时有光标、人物收起；发送一次合成消息后光标消失，大人物和北极星重新展开，回复下部在首屏外。这确认了退出聚焦布局造成的空间变化，不能等同于手机软键盘收起的实测。长历史异步锚点是否跳跃仍待验证。

**建议：** 发消息后保留键盘与焦点；导师回复期间仍允许用户写草稿，不因发送暂不可用就锁住输入。本轮不新增发送排队。明确区分“正在底部聊天”和“正在回看历史”：在底部才跟随新消息；回看时保持锚点，提供“有新消息”入口；跳转后再清未读。切换导师/群独立保存草稿与阅读位置，点击发送时绑定原会话，不能晚到后落进另一个群。

**待讨论：** 聊天页是否暂时隐藏底部主导航以增加消息空间；未确定前不强制修改导航。

### UX-07 · P1 · 私聊大人物由持续占位改为可控制的陪伴表达

**场景：** 用户多次进入同一导师的长对话，想直接看到最近内容，同时保留与导师见面的感觉。

**实现事实：** 私聊始终在消息前放北极星和大人物，聚焦输入或无障碍字号时才 compact；普通单导师人物高度 280。见 `ios/Riji/MobileViews.swift:296`，`ios/Riji/MentorDialogueStyle.swift:114`、`:158`。群页已去掉重复大场景，不代表私聊也已做同样处理。

**之前：** 每次打开长对话 → 仍有完整人物与方向区域 → 再找消息。

**建议：** 人物在首次空态保留仪式感；已有聊天默认紧凑顶部，点导师头像或“看看导师”可手动展开；再收起回到原阅读位置。首页人物不受影响，不新增第二个私聊入口。

**待讨论：** 这是对既有私聊陪伴表达的新选择，尚未得到用户确认，不能直接开发替换。

### UX-08 · P1 · 群列表帮助找回最近的事

**场景：** 用户有几个成员相同但话题不同的群，隔一天回来想继续昨天的话。

**实现事实：** 群行有名称、群头像、未读和草稿，非草稿副文案是成员名单；未显示最近消息与时间。列表数据已有 `updatedAt`，没有消息摘要字段。见 `ios/Riji/MobileViews.swift:198`、`:206`，`ios/RijiCore/MobileRoundtableModels.swift:4`。

**之前：** 扫群名和成员 → 进入多个群猜昨天在哪聊。

**建议：** 群名、最近消息一行、时间、未读提示；草稿优先显示“[草稿]”。没有消息时才显示成员。默认按可信最近活动排序，用户返回不因轮询突变丢失正在看的行。

**能力约束：** 最近消息只能来自服务明确返回的字段或本机已有且仍授权的消息，不能用想象的摘要占位；不为列表偷偷读取其他私聊/群。未接入字段时先保留真实成员信息，不能把设计图当真实数据。该项可能需要 API 与缓存配合，不能仅改前端即声称完成。

### UX-09 · P0 · 改群名是一个有结果的短动作

**场景：** 用户给“温柔回顾者、直率教练”改成“本周学习安排”，不知道点保存后还要不要点完成。

**实现事实：** 群详情同页有名称输入、“保存群名”和顶栏“完成”；保存成功后不因该动作自动返回；导师回复中禁用改名。见 `ios/Riji/MobileRoundtableViews.swift:265`、`:284`。本轮实测在名称末尾加“1”后直接点“完成”，重开仍是原名，期间无未保存提示；没有点击“保存群名”，不将其描述为保存失败。

**之前：** 群详情 → 编辑字段 → 保存群名 → 判断是否成功 → 完成。

**建议：** 群详情点“群名称” → 独立编辑页 → “取消 / 保存”。无改动时不能保存；成功返回群详情，群标题与首页同步更新，并短提示“群名已更新”。失败留在原处保留输入；回复中无法改名时提前解释“导师回复结束后可以改名”。

**边界：** 改名不改变群 ID、成员、历史或草稿；未知回执仍按原改名请求核对，不发新请求覆盖。

### UX-10 · P2 · 收起群聊与历史圆桌更容易理解

**场景：** 用户不常用一个群但想保留记录，或打开旧圆桌后又看到一排不同的邀请、总结与内容性质操作。

**实现事实：** 当前群详情立即执行归档/恢复；首页“已归档”切换列表。旧圆桌仍保留主持人、邀请导师、先总结、内容性质等控件，新群是直接发送与 @。见 `ios/Riji/MobileRoundtableViews.swift:274`、`:411`，`ios/Riji/MobileViews.swift:124`、`:252`。

**之前：** 猜“归档”是否删除 → 归档后返回找群；旧记录混在群列表里，但进入后的控制完全不同。

**建议：** 对用户优先用“收起群聊”，附“消息和草稿保留，可恢复”；成功短提示并提供撤销，运行中须先停止或完成的边界保留。旧记录轻标“历史圆桌”，点开仍直接看原消息；旧管理功能收进“更多”，不污染新群聊天方式。

**边界：** 归档不删除、不丢草稿、不静默终止未决回复；旧圆桌不自动转换新群、不改变成员与历史接收范围。是否将旧圆桌默认回看、如何保留续聊，待单独讨论，不直接关闭既有能力。

### UX-11 · P1 · 北极星既有方向感，也有准确的作用说明

**场景：** 用户选好阶段目标，以为导师已知道这个目标；来源变化后又误以为自己没有设过。

**实现事实：** 当前关联只留本机、不自动发送；原目录路径为选文件、选段落、核对关联，直接展示文件与段落字节限制。compact 横幅在无 verified 值时一律写“选择本阶段方向”，展开版才区分“来源待核验”。见 `ios/Riji/NorthStarAnchorViews.swift:23`、`:38`、`:86`、`:149`。实测空目标选择页的本机边界说明准确；来源失效和原目录选取尚未走查。合成资料为空不代表用户真实目标缺失。

**之前：** 看见目标挂在对话上方 → 不知道导师是否知情；异常时点进多层选取/核验说明。

**建议：** 首页继续突出北极星；聊天内是轻量方向入口。详情清楚写“我的本机方向”或真实的“已向本群分享”，不能混用。优先展示当前/最近可用目标，“从文件选择”作次级入口；技术大小限制在必要时解释。来源异常写“目标暂不可读取 · 重试”，保留原关联，不伪装成从未设置。

**边界：** 不新增默认上传、不自动把日记/目标传给模型。若以后提供“告诉这位导师 / 分享到本群”，须作为独立的用户主动动作，展示确切内容与接收范围；这属于后续能力，不以文案修改假装实现。

### UX-12 · P2 · 建群命名可选，不能增加前置负担

**场景：** 用户想建一个讨论“本周学习”的群，希望容易辨认，也可能只想选人立刻说话。

**实现事实：** 现有已批准默认是选二至四位导师，创建后用成员组合名；之后在详情改名。相同成员可建多个群。见专项 PRD `prd.md:68`，`ios/Riji/MobileRoundtableViews.swift:32`、`:43`。

**之前：** 选人 → 创建 → 进入群 → 更多 → 群详情 → 改名。

**次级建议：** 选人后提供可跳过的“群名（可选）”；留空直接沿用当前成员组合名。也可保留创建极简，把“给群起个名字”作为首次发言后的轻提示，二者择一，不同时加提示。

**边界：** 不新增必填标题、目标、背景、专题/长期类型或主持人；不由 AI 静默改群名。创建前取消仍不建群，显式创建成功即保留，失败保留选人和输入。是否增加可选命名需用户讨论，不追认为已批准 PRD 要求。

## 5. 重要状态文案草案

文案必须绑定真实状态，不凭网络请求已发出就显示成功；以下是待讨论的面向用户表达。

| 真实情况 | 建议可见文案 / 主动作 | 收入详情的内容 |
| --- | --- | --- |
| 正常阅读 | 无操作回执；姓名、正文、必要时间 | AI 身份、来源、消息详情 |
| 正在发送，尚无确认 | 消息旁“发送中…” | 原请求与重试防重复记录 |
| 网络断开，未知是否送达 | “正在确认是否送达，文字已保留” / 必要时“重新确认” | 未知状态、原请求 ID；不提供可误触的新发送 |
| 已确认未发送 | “这条消息未发送” / “重试发送” | 技术原因、保留文字 |
| 导师正在回复 | “直率教练正在回复…” / “停止回复” | 调度阶段、轮次预算 |
| 停止请求未确认 | “正在停止回复…” | 原停止请求状态 |
| 已确认停止，保留部分回复 | “已停止，收到的回复已保留” / 可用时“继续回复” | 继续的原轮次与边界 |
| 来源/权限变化 | “这段内容暂不可用” / “查看原因” | 具体失效范围；不得继续展示已失效正文 |
| AI 服务临时离线 | “AI 暂时离线，本地日记仍可使用” / “重试连接” | 凭据读取、服务请求等诊断 |
| 服务版本不支持建群 | “此服务版本暂未支持建群，已有记录仍可查看” | 服务能力信息 |
| 保存预览正在核验 | “正在准备保存预览” / 暂无确认动作 | 来源、目标版本核验过程 |
| 保存预览准备好 | “将追加到 10 月 16 日日记” + 确切 patch / “确认保存” | AI 来源与讨论时间保持可查 |
| 保存成功，收据已确认 | “已保存到 10 月 16 日日记” / “查看日记” | 幂等收据与写入来源 |
| 保存结果未知 | “正在核对保存结果，预览已保留” | 只读核对；不能立即重复追加 |
| 北极星来源暂不可读取 | “目标暂不可读取” / “重试” | 原关联与来源恢复方式 |

“未发送”只用于已确认未提交，“已保存”只用于真实写入/收据核验完成。“聊天已保留”“写入日记”“已采纳建议”不能互相替代。未配置北极星时仍可直接聊，不出现阻塞表单。

## 6. 验收场景

以下是方案通过讨论后的完整实施验收底稿；本轮仅有第 2 节所列的局部界面观察，未完成这些完整验收场景。

| 场景 | 可观察的通过标准 |
| --- | --- |
| 第一次阅读群消息 | 无常驻勾选圈；能直接认出谁在说话、哪里输入；长按能找到“保存到日记” |
| 私聊与群来回切换 | 每位导师唯一私聊；首页每群一行；独立草稿与记录不串，迟到回复回原会话 |
| 多人正常聊天与 @ | 群内导师按现有规则回应；点名只改变回应者，成员可见范围准确；无隐形主持人 |
| 连续发送两句 | 发送后键盘保持；焦点可继续输入；操作绑定原会话，不因切换误发 |
| 导师回复期间继续写 | 输入可编辑、草稿保留；发送按钮按真实状态变化，不假称已有消息排队 |
| 读历史时收到回复 | 视口不被拉走；提示新消息；主动跳转后才标记已读；更早分页不丢锚点 |
| 保存一条建议 | 同页完成编辑与版本核验，展示最终确切 patch；明确确认后才原子追加一次，保留 AI 来源 |
| 预览后再改日期/文字 | 原确认资格立即失效；新 patch 核验完成并可见后才可确认 |
| 预览后日记外部变化 | 不按过期版本写入；保留编辑并提示处理，再生成新预览 |
| 断网与未知送达/保存 | 输入、选择与预览可找回；优先只读核对原操作，不自动重发/重复追加，不显示假失败/假成功 |
| 断开、凭据失效、旧服务 | 三者文案与主动作不同；真实不可用能力不展示为已开通；本地可用能力不被误判为不可用 |
| 改名、取消、收起与恢复 | 取消不改名；保存成功标题一致；群 ID/成员/历史不变；归档可恢复并保留草稿 |
| 北极星未设、来源失效、已关联 | 都可继续聊天；异常不丢原关联；用户明确知道导师是否真正收到过目标内容 |
| 长消息、大字号、窄屏、VoiceOver | 输入、发送、停止、取消与确认可到达；不截断唯一的关键状态；触控区域至少 44 × 44；不依赖颜色/悬停识别操作 |
| 真机与模拟器 | 在同一版本分别核验键盘、滚动、触控、回前台恢复；模拟器测试不能替代真实服务与真机验收 |

不把合成 fixture 上相同回复算作模型体验验收。真实服务体验要在单独授权、正确部署和真实连接后，再评估回应长短、导师差异和交流节奏。

## 7. 两批实施建议

2026-10-16 用户授权开始修改，第一批进入本机实施与模拟器验证；不包含 Air 部署或手机安装。第二批继续待讨论。

| 批次 | 纳入项目 | 可供用户评审的结果 | 进入下一步的条件 |
| --- | --- | --- | --- |
| 第一批：先让聊天与保存容易理解 | UX-01 长按操作、UX-03 单份最终预览、UX-04 状态、UX-05 连接文案、UX-06 输入/锚点、UX-09 改名保存 | 同一条“进入群 → 连续聊 → 长按保存 → 断网恢复”的可运行模拟器流程；改群名只有清楚的取消/保存；不碰首页 F 基线与真实数据 | 对应状态/写入回归通过；用户实际看过并确认核心路径；真实服务能力差异明确 |
| 第二批：阅读、找回和管理更顺手 | UX-02 消息关系、UX-08 最近消息/时间、UX-10 收起/旧记录、UX-11 北极星选择与说明；UX-07/12 只纳入用户选定的方向 | 消息阅读、首页找群、群管理与阶段方向的完整走查；真实能力与设计示意分别标清 | API/缓存所需字段真实可用；权限边界与旧记录保留通过；模拟器与真机分开验收 |

第一批保留停止/继续和失败恢复能力，只调整常态入口与用户表达。第二批不顺手引入加减成员、自动转发私聊、跨设备同步或自动上传北极星；这些都需要独立定义。

讨论时先确定三个产品选择：是否接受左右消息布局；私聊大人物采用空态/手动展开还是继续默认展示；进入聊天是否收起底部主导航。可选命名属于较低优先级，不应延迟第一批。

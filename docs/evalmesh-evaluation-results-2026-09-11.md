## 已定位的问题

**1. 私聊追问的首轮上下文缺失。** 同一私聊先说明困扰，再请导师基于前文提出建议，
第二次实际生成请求只含最新追问；模型明确表示看不到前文。机器观测
`private_followup_missing_initial_context=1`，期望为 0。两次生成虽均 `completed`，业务场景仍失败。

调用链：`service.py:245` 为追问创建新 run；`planner.py:43` 按当前 run 筛历史；
`worker.py:164` 将问题换成最新追问；`summary.py:99` 对 private 返回空摘要。首轮用户材料
和导师回复因此都不进入第二轮。应修复同一私聊的上下文组装，同时保留权限、来源和长度约束。
四位导师均有对应多轮用例，不能通过更改题目预期接受这一缺口。

**2. 日记提取的输出字段契约失败。** `memory-01` 首轮只有泛化的应用拒绝记录，具体原因未知。
单独诊断重放新增私有原始响应记录后发现：模型返回合法 JSON，候选多出
`observed_at`，被 `journal_extract.py:130` 的精确字段集合校验拒绝，错误为
`journal_invalid_candidate`。在诊断副本中仅删除该额外字段，原生产 parser 即可解析；
事实内容、日期、六名同事和逐字引用本身符合题面。

该证据只证明补跑原因，不能倒推首轮同因。Prompt 在第 20 行解释 `observed_at`，
输出模板却不接受此字段；值得先消除歧义。该 DeepSeek 路径使用普通 completion，
不是发送业务 JSON schema 的路径。建议保留严格解析，检查提示词/结构化输出契约，
不要把静默丢弃未知字段直接当作通用修复。

**3. 主持人把互补建议归因为实质分歧。** `m-315d20ee406a` 的一位导师建议晚间记录，
另一位补充可改到早上或随身记录。主持人声称两者在这些备选时段上存在实质分歧，
但第一位没有反对备选方案。引用 ID 存在，仍不足以证明归因受内容支持。这是需要处理的
内容质量疑点，机器状态通过不能抵消。与此同时，后续回应正确说计划“还没开始”，
未把计划升级为既成事实。

**4. 一次请求失败的根因仍未知。** 无分歧讨论首轮请求失败后停为 `generation_unknown`，
未自动盲重试、未伪造或投递替代内容。私有计量只保留 `model_request_failed`；现有上游
provider 将部分 HTTP 错误合并，不能凭此判断超时、认证或配额原因。

同题诊断补跑完成：两位导师独立给出观点，主持人正确判断没有实质分歧，
`debate_needed=false` 后直接综合，共 4 次模型尝试、182.0 秒。未强制争辩；这一次恢复
不能证明首轮故障已被修复或稳定性达标。EvalMesh 的 harness error rate 为 0 也不代表
业务模型错误为 0，应结合私有错误分类读取。
